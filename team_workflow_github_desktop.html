VR认知评估系统三人协作分工与 GitHub Desktop 流程

本文档用于指导 A、B、C 三位成员并行开发一个 Web 版认知评估系统。系统采用前后端分离思路： A 负责后端数据处理，B 负责后端算法模型，C 负责前端页面与系统集成。

核心原则：A 管数据正确，B 管模型合理，C 管系统好用。

1. 项目最终目标

构建一个 Web 网页应用，能够导入 VR 行为日志和量表文件，自动完成数据匹配、特征提取、相关性分析、认知风险预测和个体报告展示。

VR日志 + MMSE/MoCA/CDR/HIS量表
        ↓
数据清洗与任务识别
        ↓
VR行为特征提取
        ↓
相关性分析与模型预测
        ↓
Web页面展示与报告导出

2. 三人总分工

A后端数据处理

负责原始数据进入系统，并变成可分析的特征表。

  • VR 日志解析
  • 四宫格 / 九宫格识别
  • 续存日志合并
  • 量表 Excel 读取
  • 被试 ID 匹配
  • 行为特征提取

B后端算法模型

负责认知评估算法、模型训练和个体风险预测。

  • 相关性分析
  • 候选特征筛选
  • MoCA 风险模型
  • 模型交叉验证
  • 特征重要性
  • 风险等级解释

C前端与系统集成

负责 Web 页面、交互、可视化和最终演示效果。

  • 前端项目搭建
  • 页面路由
  • 接口调用
  • 图表展示
  • 个体评估页面
  • 报告导出入口

4. GitHub Desktop 协作流程

4.1 第一次加入项目

  1. 组长在 GitHub 创建仓库，例如 vr-cognitive-assessment。
  2. 组长把 A、B、C 都添加为仓库 Collaborator。
  3. 每个人打开 GitHub Desktop，选择 File → Clone repository。
  4. 选择该项目仓库，克隆到本地统一位置。
  5. 确认当前分支是 main，点击 Fetch origin 拉取最新内容。

4.2 每个人创建自己的开发分支

成员 建议分支名 用途
A feature/data-backend 数据处理、日志解析、特征提取接口
B feature/model-backend 相关性分析、模型训练、风险预测接口
C feature/frontend-ui 前端页面、mock 数据、接口联调

GitHub Desktop 操作：点击顶部分支下拉框 → New Branch → 输入自己的分支名 → Create Branch。

4.3 每天开发前

  1. 打开 GitHub Desktop。
  2. 切换到自己的分支。
  3. 点击 Fetch origin。
  4. 如果 main 有更新，先把 main 的最新内容合到自己的分支。
  5. 确认项目能正常运行后再开始写代码。

4.4 每次提交代码

  1. 只提交自己负责目录下的文件。
  2. 在 GitHub Desktop 左下角填写 Summary。
  3. 点击 Commit to 当前分支。
  4. 点击 Push origin 上传到 GitHub。

提交信息建议：

A: add log parser and subject matching
B: add moca risk model metrics
C: add subject detail page mock layout
注意：不要直接在 main 分支上开发。每个人都在自己的功能分支工作，确认无误后再合并。

5. A 的详细步骤：后端数据处理

5.1 负责目录

backend/api/data_api.py
backend/services/log_parser.py
backend/services/scale_loader.py
backend/services/feature_extractor.py
backend/services/dataset_builder.py
outputs/correlation_analysis/
scripts/analyze_vr_scale_correlation.py

5.2 具体任务

  1. 实现 VR 日志解析，读取每一行中的时间、事件类型和 JSON 参数。
  2. 识别四宫格、九宫格任务。
  3. 处理 _log_1、_log_2 等续存日志，将同一次任务合并。
  4. 剔除空日志和无法识别的无效日志。
  5. 读取 MMSE_MoCA 文件夹中的 Excel 量表。
  6. 统一被试编号，例如 ATH010001VR 和 ATHENA010001 都转成 ATH010001。
  7. 提取 VR 行为特征，包括成功率、错误率、地图查看、路径距离、停车比例、速度和刹车等。
  8. 生成标准输出表。

5.3 A 的输出文件

文件 说明 给谁使用
log_manifest.csv 每个原始日志的任务归类结果 C 展示数据质量
scale_scores.csv 每个被试的 MMSE、MoCA、CDR、HIS B 建模，C 展示
vr_features.csv 每个被试的 VR 行为特征 B 建模
merged_dataset.csv 量表和 VR 特征合并后的总表 B 的核心输入

5.4 A 负责的接口

POST /api/data/analyze
GET  /api/data/summary
GET  /api/data/log-manifest
GET  /api/data/features
GET  /api/subjects

5.5 A 给前端的示例 JSON

{
  "subject_count": 37,
  "matched_count": 37,
  "grid4_log_count": 59,
  "grid9_log_count": 74,
  "excluded_log_count": 2
}

5.6 A 的完成标准

  • 37 名 VR 被试和 37 名量表被试能成功匹配。
  • 四宫格和九宫格日志数量统计正确。
  • 空日志不进入特征计算。
  • merged_dataset.csv 字段稳定，B 可以直接读取。
  • 接口返回 JSON 格式和 C 约定一致。

6. B 的详细步骤：后端算法模型

6.1 负责目录

backend/api/model_api.py
backend/api/report_api.py
backend/services/correlation.py
backend/services/model_trainer.py
backend/services/predictor.py
backend/services/risk_scoring.py
outputs/model_training/
scripts/train_cognitive_model.py

6.2 具体任务

  1. 读取 A 输出的 merged_dataset.csv。
  2. 完成 VR 行为特征与 MMSE、MoCA、CDR、HIS 的相关性分析。
  3. 筛选候选特征，优先使用样本量充足且有认知解释意义的指标。
  4. 构建第一版风险标签，例如 MoCA < 26 记为认知风险。
  5. 训练小样本模型，例如逻辑回归、Ridge 或 Lasso。
  6. 使用留一法交叉验证评估模型。
  7. 输出准确率、AUC、灵敏度、特异度、F1 等指标。
  8. 生成每名被试的风险概率、风险等级和关键异常特征。

6.3 B 的输出文件

文件 说明 给谁使用
correlations_reliable_n10.csv 有效样本数不少于 10 的相关性结果 C 做群体分析页面
model_predictions.csv 每名被试的风险预测结果 C 做个体评估页面
model_metrics.csv 模型性能指标 C 做模型评估页面
feature_importance.csv 重要特征及解释方向 C 做图表和解释

6.4 B 负责的接口

GET  /api/correlation
POST /api/model/train
GET  /api/model/metrics
GET  /api/model/features
GET  /api/subjects/{subject_id}/risk
GET  /api/reports/{subject_id}

6.5 B 给前端的示例 JSON

{
  "subject_id": "ATH010001",
  "risk_probability": 0.72,
  "risk_score": 72,
  "risk_level": "中高风险",
  "predicted_label": "疑似认知下降",
  "top_features": [
    {
      "feature": "grid4_wrong_pickup_rate",
      "label": "四宫格错误接客率",
      "direction": "偏高",
      "explanation": "错误接客率较高，可能提示任务执行或空间判断困难"
    }
  ]
}

6.6 B 的完成标准

  • 能基于 merged_dataset.csv 训练第一版小模型。
  • 能输出每名被试的风险概率和风险等级。
  • 能给出模型评估指标。
  • 能解释主要影响特征，而不是只输出一个黑箱分数。
  • 接口返回 JSON 格式和 C 约定一致。

7.2 具体任务

  1. 搭建前端项目，推荐 Vue 或 React。
  2. 先建立 mock JSON 文件，不等待后端完成。
  3. 完成基础页面路由和导航。
  4. 实现数据导入页。
  5. 实现数据概览页，展示被试数、匹配数、四宫格/九宫格日志数。
  6. 实现日志归类页，展示 log_manifest。
  7. 实现相关性分析页，展示重要相关指标。
  8. 实现模型评估页，展示 AUC、准确率、灵敏度、特异度。
  9. 实现个体评估页，展示单个被试的量表、VR 表现、风险评分和解释。
  10. 实现报告导出按钮或下载入口。
  11. 后端接口完成后，将 mock 数据切换为真实接口。

7.3 C 需要的页面

页面 内容 依赖谁的数据
数据导入页 选择 VR 日志和量表目录，启动分析 A
数据概览页 被试数、匹配数、四宫格/九宫格日志数 A
群体分析页 相关性排名、量表分布、特征分布 B
模型评估页 AUC、准确率、灵敏度、特异度、重要特征 B
个体评估页 某个被试的风险分数、关键异常指标、VR表现 A + B

frontend/src/mock/model_metrics.json

7.5 C 的完成标准

  • 没有后端时，前端能用 mock 数据完整演示。
  • 有后端后，能切换到真实接口。
  • 页面能清楚展示数据概览、相关性、模型评估和个体评估。
  • 个体评估页面能让用户理解风险原因。
  • 最终系统适合答辩演示。

10. 合并代码规则

  1. 每个人只在自己的分支开发。
  2. 每次提交前先确认项目能运行。
  3. 小功能完成后提交，不要堆到最后一次性提交。
  4. 合并到 main 前，先发 Pull Request。
  5. 至少让另一名成员看一眼再合并。
  6. 如果改了接口字段，必须提前通知另外两人。
  7. 不要提交大型原始数据、临时缓存、个人配置文件。
推荐提交频率：每完成一个小功能就提交一次，例如“完成数据概览接口”“完成个体详情页面”“完成模型指标输出”。

14. 答辩分工表述

A：负责后端数据处理服务，包括 VR 日志解析、四宫格/九宫格任务识别、续存日志合并、量表文件读取、被试编号匹配、行为特征提取和数据质量接口设计。
